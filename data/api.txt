  Protected — require a Sanctum token (auth:sanctum):

  ┌────────┬─────────────────┬────────────────────────────────────┐
  │ Method │    Endpoint     │              Handler               │
  ├────────┼─────────────────┼────────────────────────────────────┤
  │ GET    │ esquare/user    │ closure → returns $request->user() │
  ├────────┼─────────────────┼────────────────────────────────────┤
  │ GET    │ esquare/entries │ EntryController@index              │
  ├────────┼─────────────────┼────────────────────────────────────┤
  │ POST   │ esquare/entries │ EntryController@store              │
  ├────────┼─────────────────┼────────────────────────────────────┤
  │ POST   │ esquare/logout  │ AuthController@logout              │
  └────────┴─────────────────┴────────────────────────────────────┘

  So the flow is: call POST esquare/login to obtain a token, then send it as
  Authorization: Bearer <token> on the four protected routes.

  NOTE (2026-06-12): POST esquare/entries (EntryController@store) is DEPLOYED
  and verified end-to-end (HTTP 201, created test entry #234297 — deleted via
  admin; no API delete route exists). OPTIONS reports GET,HEAD,POST.

  Required fields (422 validation): room_id, name, start_time, end_time.
  start_time/end_time are unix timestamps (same as GET). Also accepted:
  description, entry_type, beneficiaire_ext. Any extra keys (e.g. "meta") are
  ignored by the controller.

  The WP theme is wired and live (ESQUARE_API_CREATE_PATH=entries): it forwards
  one entry per selected date. Payload built in
